## Blocker

### 1. Админские эндпоинты (`/admin/v1/**`, `/admin/v2/**`) не требуют аутентификации

- **Где:** `src/backend/app/api/admin/v1/users/routes.py:14`, `src/backend/app/api/admin/v2/maintenance/routes.py:14`, `src/backend/app/setup.py:359`, `387-408`
- **Что сломано:** `APIRouter()` создаётся без `dependencies=[Depends(...)]`, и в `setup.py` админ-приложение монтируется в `main_app` безо всякой авторизации. Любой неаутентифицированный запрос к `/admin/v1/users/` или `/admin/v2/system/health` проходит.
- **Почему это важно:** Админские эндпоинты — trust boundary; отсутствие авторизации = полный доступ к управлению пользователями/системой.
- **Как чинить:**
  1. Создать `app/utils/admin_auth.py` с зависимостью `require_admin_user`.
  2. Повесить её на оба `APIRouter(..., dependencies=[Depends(require_admin_user)])` в `admin/v1/users/routes.py` и `admin/v2/maintenance/routes.py`.
  3. Добавить в `User`/`Admin` модели признак администратора и выдавать админ-токен отдельным flow (или отдельным secret).

### 2. Redis доступен извне без пароля (`default` пользователь с `nopass`)

- **Где:** `docker-compose.yaml:184-189`
- **Что сломано:** В конфигурации Redis одновременно:
  - `requirepass ${REDIS_DEFAULT_PASSWORD}` (line 181)
  - `user default on nopass ~* +@all` (line 184)
  - порт проброшен наружу: `"${REDIS_EXTERNAL_PORT}:${REDIS_PORT}"` (line 189)
- **Почему это важно:** ACL-строка `nopass` перекрывает `requirepass` для пользователя `default`. При открытом наружном порте любой клиент может подключиться к Redis без авторизации и читать/писать все ключи (сессии, rate-limit, кеш).
- **Как чинить:**
  - Убрать `user default on nopass ...` и задать пароль для `default`:
    `user default on >${REDIS_DEFAULT_PASSWORD} ~* +@all`
  - Или вообще отключить пользователя `default` (`user default off`) и заставить приложение/healthcheck использовать именованного пользователя `${REDIS_USERNAME}`.
  - Обновить healthcheck Redis, чтобы он использовал `redis-cli -a ... ping` или `-u redis://user:pass@...`.

## Major

### 3. `/api/v1/centrifugo/subscription-token` выдаёт токен на любой канал без проверки членства

- **Где:** `src/backend/app/api/public/v1/centrifugo/routes.py:38-51`, `src/backend/app/services/centrifugo/service_v1.py:20-38`
- **Что сломано:** Эндпоинт принимает `channel` и отдаёт подписочный токен, если пользователь аутентифицирован. Нигде не проверяется, что `current_user` состоит в запрашиваемом канале.
- **Почему это важно:** Любой пользователь может подписаться на чужой приватный канал/директ, обойдя авторизацию на уровне Centrifugo.
- **Как чинить:** В `create_subscription_token` (или в сервисе) перед выпуском токена запросить `ChannelMemberRepository` и убедиться, что `(channel_id, current_user.id)` существует и `deleted_at IS NULL`. Если канал — личный (`user#<id>`), разрешить только себе.

### 4. `GET /api/v1/users/{user_id}` падает с 500 для несуществующего пользователя

- **Где:** `src/backend/app/api/public/v1/users/routes.py:58-70`, `src/backend/app/services/user/service_v1.py:87-95`
- **Что сломано:** `service.get_user_by_id()` возвращает `None`, когда пользователь не найден. Эндпоинт декларирует `response_model=UserGet`, и FastAPI пытается сериализовать `None` в модель, что приводит к внутренней ошибке (валидация ответа).
- **Почему это важно:** Нормальный сценарий API возвращает не 404, а 500. Портит контракт и логи.
- **Как чинить:** В сервисе/роуте при `result is None` поднимать `HTTPException(status_code=404, detail="User not found")` **до** возврата из функции.

### 5. Создание канала не гарантирует доступ создателю и не валидирует участников

- **Где:** `src/backend/app/api/public/v1/channel/routes.py:33-47`, `src/backend/app/services/channel/service_v1.py:22-44`
- **Что сломано:**
  - `create_channel_with_members` берёт `members` из запроса как есть; если создатель не указал сам себя, он не становится участником канала и теряет к нему доступ.
  - Если в `members` передан несуществующий `user_id`, `bulk_create` в `ChannelMemberRepository` вызовет FK-ошибку на уровне БД и вернёт 500.
- **Почему это важно:** Создатель канала ожидает, что канал "его". Несуществующие участники — обычный сценарий опечатки/мошенничества.
- **Как чинить:**
  - В `create_channel_with_members` добавлять `current_user.id` в `members` (если отсутствует) с ролью `ADMIN`.
  - Проверить все `user_id` в `members` через `UserRepository.read_by_ids(...)` и отдавать 400 с понятной ошибкой, если кого-то нет.

### 6. `min_length` в схемах регистрации/авторизации игнорируется

- **Где:** `src/backend/schemas/base.py:16`, `src/backend/schemas/users/user_register.py:18-23`, `src/backend/schemas/users/user_auth.py:16-18`
- **Что сломано:** Поля используют тип `NonEmptyString = Annotated[str, StringConstraints(min_length=1)]`, а поверх него пытаются навесить `Field(min_length=3)` / `Field(min_length=8)`. В Pydantic метаданные `Annotated` перекрывают `Field`, поэтому минимальная длина остаётся равной 1.
- **Почему это важно:** Требования "username ≥ 3" и "password ≥ 8" не работают; пользователи могут регистрироваться с паролем из одного символа. Это дыра в trust boundary входных данных.
- **Как чинить:**
  - Вариант А: добавить отдельные типы `Username = Annotated[str, StringConstraints(min_length=3, max_length=...)]` и `Password = Annotated[str, StringConstraints(min_length=8)]` и использовать их вместо `NonEmptyString + Field(min_length=...)`.
  - Вариант Б: убрать `StringConstraints(min_length=1)` из `NonEmptyString` и полагаться на `Field(...)`.

### 7. Обработчики исключений для API редиректят на `/auth`

- **Где:** `src/backend/app/handlers/exception_handlers.py:29-38`, `49-57`
- **Что сломано:** `unauthorized_exception_handler` и `forbidden_exception_handler` возвращают `RedirectResponse("/auth")` для **любого** запроса, включая API под префиксом `/api/**`. JSON-клиенты получают 302 вместо 401/403 с JSON-body.
- **Почему это важно:** Нарушает REST-контракт и затрудняет отладку фронтенда/мобильного клиента.
- **Как чинить:** В обработчиках проверять `request.url.path`. Для путей, начинающихся с `/api/`, возвращать `JSONResponse(status_code=401/403, content={"detail": ...})`. Редирект оставить только для HTML-роутов (`/`, `/admin/login` и т.п.).

### 8. Soft-delete не освобождает `username`/`email`, блокируя повторную регистрацию

- **Где:** `migrations/versions/2026-03-01-19-28-fe9642e7d89d_initial.py:71-72`, `src/backend/app/models/user.py:31-33`, `src/backend/app/services/user/service_v1.py:126-140`
- **Что сломано:** Уникальные индексы `ix_users_email` и `ix_users_username` не являются partial-индексами: они проверяют уникальность по всем строкам, включая soft-deleted (`deleted_at IS NOT NULL`). После удаления пользователя его email/логин нельзя использовать для нового аккаунта.
- **Почему это важно:** Soft-delete ломает обычный UX-сценарий "удалил аккаунт и зарегистрировался снова".
- **Как чинить:**
  - Создать новую миграцию, которая удалит старые уникальные индексы и добавит `sa.Index('ix_users_email', 'email', unique=True, postgresql_where=sa.text('deleted_at IS NULL'))` (или эквивалент через `UniqueConstraint(postgresql_where=...)`).
  - Для SQLite (тесты) partial index поддерживается с `sqlite_where`.
